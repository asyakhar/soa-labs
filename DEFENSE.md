# Замечания преподавателя и ответы для защиты

## Что изменено

- GET/HEAD: ошибки проверки параметров описаны через 422, без 400 в контракте.
- DELETE билета: 204 и при удалении, и при отсутствии билета; 404 убран.
- PUT уже существовал. Добавлены HEAD билета и OPTIONS коллекции: всего 12 операций.
- GET/HEAD билета поддерживают If-None-Match, ETag и 304 без тела.
- Ошибки содержат конкретные условия и примеры; violations показывает поля и причины.
- Дата и время представлены строкой dd.MM.yyyy HH:mm:ss, допускаются доли секунды.
- Swagger UI показывает структуру схем, понятные названия и примеры значений.

## 400 и 422 на уровне модели

400 Bad Request — сервер не может обработать запрос из-за ошибки клиента. Это общий статус, в частности для ошибки синтаксиса запроса.
422 Unprocessable Content — синтаксис содержимого понятен, но указания в нём нельзя обработать, например данные нарушают схему.

В нашем POST/PUT:

- ticket отсутствует, JSON-текст не завершён или имя свойства записано без двойных кавычек → 400; модель ещё не проверяется.
- JSON разобран, но price содержит строку "дорого", число -10, отсутствует обязательный name, comment длиннее 341 символа или type равен null → 422.

422 не означает исключительно «неверный тип»: сюда относятся также диапазоны, длины, обязательность и допустимые значения enum. Выбор статуса не включает и не отключает валидацию. Сначала определяются этап и причина отказа, затем обработчик сопоставляет им статус. Некоторые фреймворки по умолчанию возвращают 400 даже при ошибке привязки типа — для нашей политики понадобится обработчик ошибок.

Для GET/HEAD 422 на ошибки параметров — отдельное соглашение учебного API. HTTP не запрещает GET возвращать 400. Ошибки самого HTTP-сообщения, обнаруженные прокси или сервером до вызова операции, также могут привести к 400 независимо от метода.

## Можно ли вернуть 404, если в запросе участвует id?

Да, если искомый ресурс не найден, независимо от наличия тела запроса или метода. Но само наличие id не означает 404: буквенный id вместо целого — ошибка проверки параметра (у нас 422), а положительный id отсутствующего билета — 404 при GET/HEAD/PUT/продаже.

У нашего DELETE выбран другой контракт: отсутствие билета считается достигнутым результатом, возвращается 204. Стандарт допускает и 404 для DELETE; идемпотентность относится к результату на сервере, а не к обязательному совпадению статусов повторных запросов.

## Что такое ответы 3xx?

Это класс перенаправлений, а не ошибок. Не нужно добавлять произвольный 300 каждой операции.
У нас 304 Not Modified применяется к условному GET/HEAD: клиент передаёт If-None-Match со значением ETag, полученным ранее; если представление не изменилось, сервер возвращает 304 без тела. При изменении возвращается 200 с новым ETag. Для обычного GET без условия используется 200. При отсутствии билета — 404.

If-None-Match — метаданные HTTP в заголовке; параметры предметной области по-прежнему находятся в URL. Это явно оговорено в спецификации.

## Как сделать время понятнее без date-time?

Использовать type: string, pattern и example: '21.09.2026 14:30:00'. Это пользовательский строковый формат, не стандартный OpenAPI date-time. В Java для вывода подходит DateTimeFormatter.ofPattern("dd.MM.uuuu HH:mm:ss"); если используются доли секунды, форматтер должен поддерживать их опционально. LocalDateTime не содержит часового пояса; timestamp ошибки в нашем контракте отдельно определён как UTC.

Регулярное выражение проверяет форму строки и диапазоны времени, но не количество дней в конкретном месяце. Например, 31 февраля должен отбрасываться календарным парсером. Фильтрация даты сравнивает разобранные даты, не строки dd.MM.yyyy.

## Проверки

npm run check: Redocly, Swagger Parser, проверки статусов/методов/формата времени и пересборка openapi.bundle.json.
Ожидаемое предупреждение Redocly operation-4xx-response для OPTIONS /tickets: нет параметров, в контракте не придуман отдельный сценарий 4xx.

Это спецификация: реализация API и обработчики ошибок не добавлены. Для обновления опубликованной документации нужно загрузить новую сборку на Helios.
